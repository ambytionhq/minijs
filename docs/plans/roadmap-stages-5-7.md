# Roadmap: Stages 5 to 7 (outline)

Status: superseded by the full plans `stage-5-studio.md`, `stage-6-desktop.md`, `stage-7-flagship.md` (2026-10-06). Projects in the browser, disk folders and picture import moved forward into Stage 4b (`stage-4b-inputs-files.md`). This outline stays as the short version. Stages 1 to 4 are the engine; these stages turn it into something people install, carry around, and play.

The user asked for three ways to make and play minijs games with no internet:

1. In the browser, offline.
2. Download the source code and run it locally.
3. A cross-platform app (macOS, Windows, Linux).

Plus one really good game that shows off the engine.

## Stage 5: minijs Studio (offline web app)

Grows the Stage 4 playground into the real editor. Same code, more product.

- **Installable PWA.** Web manifest + service worker that precaches the app shell, fonts, runtime, and examples. After the first visit it works with no network. "Install" button where the browser supports it.
- **Projects, not one text box.** A project is a `.mini` file plus its images. Stored in IndexedDB (localStorage is too small for images). Project list, new, rename, duplicate, delete.
- **Image import.** Drag PNGs in; they become project assets that `looks like "x.png"` can use.
- **Export a game** as one standalone `.html` file: runtime, compiled program, and images (as data URIs) inlined. Double-click it on any computer and the game runs offline. No editor inside, just the game, fullscreen and scaled.
- **Export/import a project** as a `.zip` (`game.mini` + `assets/`), so people can share source and open it again in the Studio.
- **Download the source code.** README section and a `npm run build` that produces a static `dist/` folder. Serve it with any static server, or open the exported files directly.
- Keyboard shortcuts (run, stop, restart), a short in-app language reference panel, share-by-link for small projects (source in the URL hash, no server).

Done when: Studio works fully offline after one load (verified with the network turned off), a game exported to `.html` runs from `file://`, and a project zip round-trips.

## Stage 6: Desktop app (cross-platform)

The Studio as a native app for macOS, Windows, and Linux.

- **Shell: Tauri 2 (recommended)** over Electron. Tauri apps are about 5 to 15 MB because they use the system web view; Electron bundles Chromium (about 100 MB+). The Studio is plain web code, so either works; Tauri keeps downloads small.
- Real files instead of IndexedDB: open/save `.mini` projects as folders, recent projects, file associations for `.mini`.
- **Export a game as a desktop app.** The desktop app ships a prebuilt "player" (the same shell with only the game view). Export copies the player for the chosen platform and puts the game next to it, so no compilers are needed on the user's machine. The HTML export from Stage 5 remains the universal option.
- GitHub Actions builds installers for all three platforms on tagged releases (`.dmg`, `.msi`/`.exe`, `.AppImage`/`.deb`).
- Open question for the user at stage start: code signing. Unsigned macOS/Windows apps show security warnings; signing needs an Apple Developer account and a Windows certificate.

Done when: installers build in CI for all three platforms, the app opens/saves projects on disk, and an exported game launches as its own app.

## Stage 7: Flagship game (and the engine features it needs)

One polished game written in `.mini`, shipped as an example, an HTML export, and a desktop export. Its job is to prove the engine is fun, and to find what the language is missing.

- Working idea: a short arcade platformer, several screens, enemies, collectibles, a timer, a win screen, hand-made pixel art generated by script.
- Before writing it, list the features it needs that v1 lacks (spec section 1 non-goals). Likely candidates: **sound effects**, **multiple levels or rooms**, **per-thing numbers** (an enemy's own health), **text size**. Each one added goes through the normal path: spec change, AST change, lang + runtime + tests.
- The user decides which features to add at stage start; the game is designed around what exists after that.

Done when: the game is fun to play start to finish, compiles with zero problems, runs at 60 ticks/s on a low-end laptop, and ships in all three forms.
